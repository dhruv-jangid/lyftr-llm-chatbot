# LLM Chatbot with Key Failover and Response Caching

A full-stack chatbot. The frontend is **React (Vite)**, the backend is **Python FastAPI**, and **LiteLLM** handles key failover and response caching. Chat history is stored in **SQLite**, and the whole stack runs with **Docker Compose**.

```
React (Vite) ──HTTP/JSON──▶ FastAPI ──▶ LiteLLM Router ──▶ Gemini (key_1 → key_2 → …)
                               │              └── LiteLLM in-memory cache
                               └── SQLite (/data/app.db on a named volume)
```

## 1. Live URLs

- Frontend: https://lyftr-llm-chatbot-ten.vercel.app
- Backend: https://lyftr-llm-chatbot-production.up.railway.app (try [`/health`](https://lyftr-llm-chatbot-production.up.railway.app/health))

The frontend is hosted on Vercel and the backend runs on Railway from `backend/Dockerfile`. A Railway volume is mounted at `/data`, so the SQLite file survives redeploys.

## 2. Run locally

### With Docker (recommended)

```bash
cp .env.example .env        # then put your 2+ real keys in LLM_API_KEYS
make up                     # builds and starts both containers
```

- Frontend: http://localhost:3000
- Backend: http://localhost:8000/health

`make down` stops everything. Chat history stays in the named volume `chat-data`, so it survives restarts. `make logs` follows the logs, and `make test` runs the backend tests inside a Python container.

### Without Docker

Backend (Python 3.11+):

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp ../.env.example .env     # edit keys; set DATABASE_URL=sqlite:///./data/app.db
uvicorn app.main:app --reload --port 8000
python -m pytest            # 24 tests, no real API calls
```

Frontend (Node 20+), in a second terminal:

```bash
cd frontend
npm install
npm run dev                 # http://localhost:5173 (VITE_API_URL defaults to http://localhost:8000)
```

### Environment variables

| Variable | Meaning |
|---|---|
| `LLM_API_KEYS` | Comma-separated key pool (≥ 2). Ids are `key_1`, `key_2`, … in this order |
| `LLM_MODEL` | LiteLLM model name, default `gemini/gemini-3.5-flash-lite` |
| `DATABASE_URL` | SQLite location, e.g. `sqlite:////data/app.db` |
| `ALLOWED_ORIGINS` | Comma-separated CORS origins |
| `ENABLE_FAILURE_SIMULATION` | `true` enables the `X-Simulate-Failure` header |
| `DEFAULT_SYSTEM_PROMPT`, `LLM_TIMEOUT_SECONDS` | Optional |
| `VITE_API_URL` (frontend, build time) | Public backend URL |

## 3. Design decisions

### Key fallback (LiteLLM Router)
- Each API key is registered as its own LiteLLM Router model group (`key_1`, `key_2`, …). All groups use the same model, and only the `api_key` differs. The real key is never returned or logged, only its id.
- `Router(fallbacks=[{"key_1": ["key_2", ...]}], num_retries=0, disable_cooldowns=True)`. Every request starts on `key_1`. On any provider error (429 rate limit, quota exhausted, 5xx, timeout), LiteLLM moves straight on to the next key without retrying the failing one.
- The key that answered is read from the response's `model_id`, which we set to the key id. Keys are always tried in order, so `fallback_attempts` equals that key's position (key_2 means 1 key failed first).
- If every key fails, the API returns `503 {"detail": "all providers unavailable"}` and nothing is written to SQLite.
- **`X-Simulate-Failure`** (only when `ENABLE_FAILURE_SIMULATION=true`): the header is parsed (`key_1=429`, `key_1=429,key_2=500`, `*=429`; statuses 429/500/502/503). For that one request we build a short-lived Router in which the named keys use LiteLLM's `mock_response` to raise a real `RateLimitError` (429) or `InternalServerError` (5xx). The healthy keys still call the real model, so the reply is genuine. No global state changes, so other requests are unaffected. Simulated requests skip the cache *read*, so they really exercise the keys and show `key_2` (or a 503). Without that, a cached answer would hide the failover.

### Caching (LiteLLM built-in)
- `litellm.cache = Cache(type="local")` turns on LiteLLM's in-memory cache, and each call passes `caching=True`.
- LiteLLM builds the cache key from the model and the **full message list** we send: system prompt + SQLite history + new message. So the same first message in a new session is a hit, while a different message, a different system prompt or a different history is a miss.
- `caching_groups=[(model, "key_1", "key_2", ...)]` lets all key groups share one cache, so a reply generated by key_2 is still reused later.
- A cache hit is detected from `response._hidden_params["cache_hit"]`. It returns `resolution_source = LLM_CACHE`, `key_id = null`, `fallback_attempts = 0`, the identical text, and the token usage stored with the cached response. Latency drops from hundreds of ms to a few ms.
- Trade-off: an in-memory cache is cleared when the process restarts. That is acceptable here, and Redis is not allowed by the brief.

### SQLite session storage
- The `messages` table follows the required schema, plus an index on `(session_id, id)`. A small `sessions` table keeps the custom system prompt per session. The system prompt is never returned by the history endpoint.
- Both tables are created on startup (`CREATE TABLE IF NOT EXISTS`). Timestamps are ISO-8601 UTC, and assistant metadata is stored as JSON text.
- The client sends only the new message. The backend loads the history (oldest first), builds the prompt, calls the LLM, and **only on success** saves the user and assistant messages in one transaction. Failed requests (422/503) are therefore never stored.
- The file lives at `/data/app.db` on the named Docker volume `chat-data` (a Railway volume in production).

### Validation and errors
- Pydantic validates `session_id` (1–128 chars, not blank) and `message` (1–4000 chars after trimming). Errors return 422 in FastAPI's default `{"detail": [...]}` shape, and malformed JSON is also 422.
- Custom exception handlers make sure every error is JSON with a `detail` field. There are no stack traces or HTML error pages.

## 4. Verification

```bash
B=https://lyftr-llm-chatbot-production.up.railway.app   # or http://localhost:8000
curl -s $B/health

# Live inference, then a cache hit (same first message, new session)
curl -s -X POST $B/chat -H 'Content-Type: application/json' -d '{"session_id":"s-a1","message":"What is the capital of France?"}'
curl -s -X POST $B/chat -H 'Content-Type: application/json' -d '{"session_id":"s-a2","message":"What is the capital of France?"}'
#   -> 2nd: "resolution_source":"LLM_CACHE", "key_id":null, same reply, smaller latency_ms

# Failover
curl -s -X POST $B/chat -H 'Content-Type: application/json' -H 'X-Simulate-Failure: key_1=429' -d '{"session_id":"s-b1","message":"Say hi"}'
#   -> 200, "key_id":"key_2", "fallback_attempts":1
curl -s -i -X POST $B/chat -H 'Content-Type: application/json' -H 'X-Simulate-Failure: *=429' -d '{"session_id":"s-b2","message":"Say hi"}'
#   -> 503 {"detail":"all providers unavailable"}

# Multi-turn + history
curl -s -X POST $B/chat -H 'Content-Type: application/json' -d '{"session_id":"s-c1","message":"My name is Dhruv."}'
curl -s -X POST $B/chat -H 'Content-Type: application/json' -d '{"session_id":"s-c1","message":"What is my name?"}'
curl -s $B/sessions/s-c1/messages
curl -s -i $B/sessions/unknown/messages        # 404 {"detail":"session not found"}
```

**Token usage:** every assistant reply in the UI shows `input_tokens` and `output_tokens` for that request only. They also appear in each assistant message's `metadata` from the history endpoint. `input_tokens` grows as the conversation history grows, because the whole history is part of the prompt. `output_tokens` covers only that reply.

**In the UI:** open *Session settings* and pick a value in *Failover demo* to send `X-Simulate-Failure` from the browser. Every reply shows chips for source, model, latency, input/output tokens and the key used.

**Automated tests:** `cd backend && python -m pytest` runs 24 tests covering health, validation, multi-turn, session separation, cache hit/miss, real and simulated failover, 503, the no-store-on-failure rule, token metadata and SQLite persistence. The tests talk to a fake OpenAI-compatible server over real HTTP, so they exercise the real LiteLLM router and cache without spending credits.

## 6. Bonus features

- **Failover demo selector in the UI.** It sends `X-Simulate-Failure` from the browser, so failover and the 503 path can be shown without curl.
- **Key and failover chip on each reply** (`key_2 · 1 failover`), which makes fallback visible at a glance.
- **"New chat" button** that starts a fresh session without reloading.
- **Per-session system prompt** (`system-prompt-input`). It is stored server-side and reused for later turns, but never exposed.
- **Markdown rendering** of assistant replies (react-markdown), so lists and bold text from the model display cleanly.
- **Tests against a fake HTTP LLM server** instead of mocking LiteLLM itself, so the real router and cache code paths are tested.
